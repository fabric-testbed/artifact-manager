Create an artifact

Sign in with your FABRIC account, then choose Create Artifact on the Artifacts page. Creating artifacts requires a FABRIC account with JupyterHub access. Give it a title, a short and a long description, tags, and a visibility:

  • Author - only the artifact's authors can see it.
  • Project - authors and members of the chosen FABRIC project.
  • Public - everyone, including people who are not signed in.

Clearing Show Authors or Show Project hides them from non-authors, for double-blind review. Authors can add co-authors by their FABRIC user UUID on the artifact's Edit page; every author can manage the artifact.

Versions

An artifact holds one or more versions. Each version is a single archive with a permanent URN, downloadable by anyone allowed to see the artifact.

  • Upload - on the artifact page, use Add a new Version with a .tgz or .tar.gz file.
  • Import from GitHub - copy the source of a release or tag from a linked repository (below), by hand or automatically.
  • Disable / enable - a disabled version stays recorded but cannot be downloaded. Uploaded and GitHub versions can live side by side.

Link a GitHub repository

On the artifact page, an author enters owner/repo or https://github.com/owner/repo under Link a GitHub repository and chooses Link repository. Only public repositories on github.com can be linked, and each artifact links at most one.

Linking trusts the repository: anyone with write access to it can publish new versions of this artifact through GitHub Actions. Link only repositories whose collaborators you would also trust as authors.

Versions published this way are credited to the author who linked (or last re-confirmed) the repository. If that person stops being an author, the page shows Publishing paused until a current author chooses Re-confirm; the same applies if the repository is transferred or recreated. A plain rename is followed automatically. Unlink stops publishing and keeps every version already imported.

Import releases and tags by hand

Under GitHub releases and tags, choose Show releases and tags. The list shows published GitHub Releases first (with their name, date and any pre-release badge), then every git tag that has no Release, marked tag. Choose Import on a row to copy that version's source archive into FABRIC storage.

  • A release import keeps the release's name, publication date and pre-release flag.
  • A tag import records the tag, its commit and the commit date. Draft releases count as plain tags.
  • Importing a tag that is already imported returns the existing version; nothing is duplicated.

Publish automatically with GitHub Actions

You do not need to create, copy or store any token. No repository secret, no FABRIC token, no personal access token. Each workflow run asks GitHub for a short-lived identity token (OpenID Connect) that proves which repository it is running in, and the Artifact Manager checks that it is the repository linked to your artifact. The only requirement is the permissions: id-token: write line already in the workflow.

  1. Link the repository to the artifact.
  2. On the artifact page, expand Publish automatically with GitHub Actions and choose Copy workflow. That copy already contains this site's address and your artifact's UUID.
  3. In the repository, save it as .github/workflows/publish-artifact.yml and commit it to the default branch.
  4. Publish a GitHub Release, or push a tag (git tag v1.2.0 && git push origin v1.2.0). The workflow runs and the new version appears on the artifact page within a minute or two.

For reference, the workflow looks like this; the artifact page fills in the UUID for you:

{{ workflow }}

Things worth knowing:

  • It runs from the tagged commit. GitHub runs the workflow file as it exists in the commit being released or tagged, so tags made before the workflow was committed will not publish themselves; import those by hand.
  • Releases and tags together. Creating a Release usually pushes its tag too, so two runs start. Whichever finishes first creates the version; the other finds it and succeeds without a duplicate. If the tag run wins, the version carries the tag's details rather than the release name.
  • Pull requests never publish. Runs triggered by pull_request or pull_request_target are refused, so forks cannot publish to your artifact.
  • Organization policies. If your GitHub organization restricts Actions, it must allow this workflow to run; no other repository or organization setting is needed.

Scripting with the REST API

Everything on the artifact page can also be done through the API, documented interactively at /api/swagger/. Authenticate with your FABRIC token: in the FABRIC Portal, open Experiments › Manage Tokens, create a token and use its id_token value. Treat it like a password and never commit it to a repository.

export FABRIC_TOKEN='...'   # id_token from the FABRIC Portal

# List an artifact's GitHub releases and tags
curl -sS -H "Authorization: Bearer $FABRIC_TOKEN" \
  {{ api_root }}/artifacts/<artifact-uuid>/repo/releases

# Import one of them as a new version
curl -sS -X POST -H "Authorization: Bearer $FABRIC_TOKEN" -H 'Content-Type: application/json' \
  --data '{"tag": "v1.2.0"}' \
  {{ api_root }}/artifacts/<artifact-uuid>/repo/import

An import made this way is credited to you, and you must be an author of the artifact.

Troubleshooting GitHub publishing

When a publish run fails, open it in the repository's Actions tab: the last lines of the Publish step show the HTTP status and the Artifact Manager's message.

StatusMessageWhat to do
- The step fails before contacting this site, at the token request. The workflow is missing permissions: id-token: write, or it ran for a pull request from a fork, which GitHub never gives an identity token.
401 Invalid GitHub Actions token. AMGR_URL in the workflow must match this site's address exactly. Re-copy the workflow from the artifact page.
403 GitHub publishing is not permitted. The run is not from the repository linked to this artifact (a fork, a different artifact UUID, or a transferred or recreated repository), the repository is private, publishing is paused, or it was a pull-request run. Check the UUID and the repository card on the artifact page; Re-confirm if asked.
404 GitHub tag was not found. The tag does not exist on GitHub (yet). Push it, then re-run the workflow.
409 An operation on this artifact is in progress; please retry. Another import was running; the workflow retries on its own. If it still fails, re-run it.
409 The GitHub repository identity changed; an author must re-confirm the link. An author chooses Re-confirm on the artifact page.
413 GitHub archive exceeds the import size limit. The source archive is over {{ import_max_mib }} MiB. Move large data out of the repository, or upload a trimmed .tgz by hand.
429 This artifact has reached its daily GitHub import limit. Wait until after midnight UTC, then re-run the workflow.
503 GitHub is refusing requests / imports are busy / signing keys unavailable Temporary. The workflow retries; if it still fails, re-run it later.

Limits

  • Public repositories on github.com only; GitHub Enterprise is not supported.
  • Source archives up to {{ import_max_mib }} MiB. Release assets (files attached to a Release) are not imported - only the repository source at that commit.
  • {{ imports_per_day }} new GitHub versions per artifact per UTC day, shared by the web page, the API and Actions. Re-importing an existing tag does not count.
  • The list shows up to 500 releases and up to 500 other tags; older ones can still be imported by name through the API.
